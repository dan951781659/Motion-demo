# Motion 规则页（HTML）评审报告与优化方案

- 评审对象：`motion-demo-current/index.html` 右侧「当前页面功能规则」面板 / `rules.html` 总览
- 对照基准：`Motion设备端V2.2.0与APP-V1.2.0最终PRD.md`（最终评审版，2026-11-04，607 行）
- 评审日期：2026-11-04
- 评审方法：① PRD 逐段与 `rulebook-data.js` 做文本覆盖度比对（10 字滑窗）；② 12 个模块人工逐条核对；③ Playwright 实测渲染 DOM、表格完整性、控制台报错
- 结论：**网页已覆盖 12 个模块的全部模块内规则，未发现模块内规则被删漏；缺的是 PRD 的 4 个全局章节，以及约 20 处规则本身的判定口径。** 共 36 项问题：阻断 4 项、高 16 项、中 10 项、建议 6 项。

---

## 一、总体结论

| 维度 | 结论 |
| --- | --- |
| 模块内规则（8 段结构） | 12/12 模块齐全，无整段缺失；文本与 PRD 基本逐句一致 |
| PRD 全局章节 | **4 章全部缺失**（版本目标与范围、主要操作流程、发布前待确认事项、验收口径） |
| 规则可执行性 | 13 处「沿用原…」无基线引用，11 处「待确认」散落正文且无汇总登记，评审无法逐条判定通过 |
| 可追溯性 | 无需求编号，规则条目无法与用例/RTM 对应 |
| 渲染与工具 | 表格可正常显示；但 AI 训练模块 HTML 存在非法嵌套，编辑/导出会持续传播脏结构；编辑器无「恢复原始」 |

**一句话结论**：网页现在的定位是「12 个模块的变更说明」，而 PRD 是「一次版本发布的完整需求说明」。差的不是模块内容，而是**版本级上下文（范围/主流程/待确认/验收口径）**和**规则判定的量化口径**。

## 二、A 类：PRD 有、网页缺（迁移缺项）

### A-01 版本目标与范围（阻断）

- PRD 位置：第 7–16 行（含「端 × 本次模块」对照表、三 Tab/四 Tab 保留说明、Demo 样例声明）
- 网页现状：无。左栏只有模块入口，评审看不到「本次发布了什么、哪些端、什么范围内」
- 影响：评审第一问「这次一共改了哪些」无法在页面内回答，必须回读 PRD，违背网页「无需另读 PRD」的设计目标
- 优化方案：新增模块 `版本目标与范围`，置于左栏首位（`rules` 总览之前），内含：本次范围一句话 + 端×模块表 + 三/四 Tab 保留 + 样例数据声明

### A-02 主要操作流程（阻断）

- PRD 位置：第 18–23 行（准备内容 / 开始动作 / 床体操作 / 注销账号 4 条主链路）
- 网页现状：无。各模块写了局部流程，但跨模块主链路（尤其「准备 → 开始动作 → 训练」串联）无处可看
- 影响：研发按模块实现易漏掉跨模块前置条件（如训练准备缺省时仍有 5 项安全门禁）
- 优化方案：新增模块 `主要操作流程`，用表格 `流程 | 步骤链路 | 关键判定` 呈现 4 条链路，并在「训练准备」「床体控制」「APP 账号注销」三个模块首行加「主流程见《主要操作流程》第 N 条」

### A-03 发布前待确认事项（阻断）

- PRD 位置：第 592–601 行（6 行汇总表：动作库 / 训练数据 / AI / 硬件 / 常见问题 / 注销）
- 网页现状：无汇总，11 处「待确认」散落在各模块正文（如「服务端错误分类待确认」「回传字段、有效期及固件重锁时长待确认」）
- 影响：这是评审最需要的一页——「哪些点没定、谁去定、定了才能开发」。散落写法导致无法清点，也无法跟踪关闭
- 优化方案：新增模块 `发布前待确认事项`，作为**唯一登记处**：
  1. 表格列：`编号 | 模块 | 待确认内容 | 影响范围 | 责任方 | 最晚确认时间 | 状态`
  2. 各模块正文只保留引用，如「错误分类见 待确认 #LIB-03」，不重复描述
  3. 在规则页顶部加一行计数：「待确认 6 类 / 21 项，其中阻塞开发 8 项」

### A-04 验收口径（阻断）

- PRD 位置：第 603–607 行（总体验收原则 + 评分一致性约束 + 截图与模拟说明）
- 网页现状：各模块有「验收与演示」，但缺全局口径（尤其「评分等级文字与圆环分数来自同一次结果，切语言/暂停恢复/无法识别时保持一致」这条跨模块一致性要求）
- 优化方案：新增模块 `验收口径`，含：① 验收方式（按各模块验收段执行，正式发布需真机/真账号/真后台）② 三条跨模块一致性约束 ③ 截图与模拟数值免责说明

### A-05 页头缺版本信息（重要）

- PRD 第 3–5 行有「版本 / 日期 / 依据」
- 网页仅顶部右上角有「设备 2.2.0 / APP 1.2.0」标签；右侧规则区无版本号、无日期、无依据说明，也无变更记录
- 优化方案：规则面板头部固定一行元信息：`最终评审版 · 2026-11-04 · 依据 motion-demo-current 最新 Demo`，并在 `rules.html` 顶部同样展示；后续每次改规则追加一行变更记录

### A-06 章节名不一致：「功能说明」→「本次修改」（重要）

- 12 个模块全部把 PRD 的「功能说明」改成了「本次修改」
- 实测：多数模块两段文字内容相同（如床体控制两处均为「设备全局快捷面板内提供床体位置与轨道锁。」），属**改名不丢内容**；但语义变了——「功能说明」定义能力边界，「本次修改」只说明变更，评审看「这次改了什么」时容易把「功能说明」当成变更描述
- 优化方案（二选一，推荐 B）：
  - A. 统一改回「功能说明」，变更信息另设「本次变更点」小节
  - B. 保留「本次修改」，但在其下补一行「当前能力：…」，形成 `本次修改 → 当前能力 → 页面与状态` 三段式

### A-07 章节层级不一致（重要，源文档即有）

- PRD：`### 页面与状态` 之下，只有「主画面与小画框」是 `####`，而「圆环评分与动效」「消息与语音」「无法识别完整动作」写成了 `###`（与「操作规则」同级）
- 网页忠实继承了这个错误：实测渲染后 H3 顺序为 `页面与状态 → H4 主画面与小画框 → H3 圆环评分与动效 → H3 消息与语音 → H3 无法识别完整动作 → H3 操作规则`，视觉上「圆环评分」与「操作规则」平级，但语义上它是「页面与状态」的子项
- 影响：评审按目录跳读时会误判章节归属
- 优化方案：把这 4 个子项统一为 H4（或统一为 `页面与状态：主画面 / 页面与状态：评分 / 页面与状态：消息 / 页面与状态：失识别`），PRD 与网页同步修改

## 三、B 类：规则不清晰 / 冲突 / 边界缺失

> 下列问题在 PRD 与网页中**同时存在**（网页只是转载），因此需要回到规则本体修订。每条给出可直接落地的写法。

### B-01 床体控制：人确认与传感器谁说了算（高）

- 位置：床体控制 → 操作规则 / 适用条件
- 现状：「折叠／展开前**确认**床上无人且周围无遮挡」（谁确认未写）；结尾又写「不能用**用户确认**代替传感器」
- 冲突：前者像让用户点确认，后者明确禁止用确认代替传感
- 建议写法：
  > 折叠／展开采用双闸门：闸门一「人因确认」——点击后弹确认框「请确认床上无人、周围无遮挡」，需二次确认；闸门二「传感校验」——固件返回的推入/位置/锁定/床上承重（如有）状态必须新鲜且满足条件。两闸门均通过才下发命令；传感器能力缺失时以「无可靠证据 → 禁用」处理，不允许仅凭用户确认放行。

### B-02 床体控制：「状态新鲜」无阈值（高）

- 现状：「状态新鲜」是判定前提，但全文无定义；PRD 汇总表只写「回传有效期待确认」
- 建议：补「新鲜 = 距最近一次回传 ≤ 2s（占位，待固件确认）；超时即视为未知，按钮禁用并显示『设备状态同步中』；恢复回传后自动解除」
- 同步动作：把该阈值登入「待确认 #HW-01」，模块内只引用编号

### B-03 床体控制：缺状态机（高）

- 现状：5 个状态（已展开/已折叠/中途停止/移动中/未知）只有并列描述，没有迁移关系
- 影响：研发会各自实现，测试无法穷举
- 建议：补 6 行迁移表——`当前状态 | 触发事件 | 目标状态 | 允许操作 | 失败/超时回退`

| 当前 | 事件 | 目标 | 失败/超时 |
| --- | --- | --- | --- |
| 已展开 | 折叠确认通过 | 移动中（折叠方向） | 命令未受理 → 停留已展开并提示 |
| 移动中 | 收到停止回传 | 中途停止 | 结果未知 → 停留移动中 + 现场处置提示 |
| 中途停止 | 继续（同方向）确认 | 移动中 | 同上 |
| 已展开 | 解锁确认 | 解锁倒计时 | 倒计时到 0 未回传 → 重锁等待 |
| 重锁等待 | 回传已锁定 | 已展开（锁定） | 超时 → 锁定超时，禁止恢复训练 |
| 任意 | 断连 | 未知 | 禁止新命令；重连仅同步不重放 |

### B-04 系统性缺失：命令类操作的「等待态 / 超时 / 回退」范式（高）

- 涉及：床体折叠/展开/解锁、弹簧切换、背景音乐音量写入（均已写「命令受理 ≠ 完成」，但都没给超时值与失败态）
- 建议：新增一节「命令时序规范」（放在《主要操作流程》之后，全局生效）：
  > 所有设备写入类命令统一三态：`已下发（按钮禁用 + 加载态）→ 已确认（用回传值刷新 UI）→ 未确认（超时 N 秒 → 保留上次生效值 + 提示重试 + 提供现场处置入口）`。超时值按命令分级，登记在待确认表。**任何情况下不得用乐观更新显示成功。**

### B-05 弹簧切换 × 训练数据：换阻力后的数据口径（高）

- 位置：弹簧快捷切换 → 生效与异常 / 数据来源与保存
- 现状：只写「当前选中值绑定训练会话」，未写切换后当前动作的次数/容量/输出能量如何处理
- 影响：直接决定「次数算不算断点」「容量是否按新阻力重算」，测试与数据侧都无法实现
- 建议写法：
  > 切换阻力不重置次数（次数属于动作维度，与阻力无关）。容量与输出能量按切换时刻分段：切换前的量按旧阻力结算并归入当前动作，切换后按新阻力继续累加；界面在切换后给出 1 次轻提示「阻力已切换，当前组数据分段统计」。若产品决定不分段，必须明确「切换后本组数据作废/重算」的规则并同步《训练数据与次数》。

### B-06 AI 训练：失识别没有防抖（高）

- 现状：写了「人物未完整进入镜头时显示 —」「恢复后下一有效评分才恢复」，但没写判定时间
- 影响：边界抖动会导致评分圆环与提示语高频闪烁，正好命中规则自己禁止的「循环闪烁」
- 建议写法：
  > 进入失识别：连续 800ms 未检测到完整部位（或置信度低于阈值）才切换；退出失识别：连续 3 帧有效且置信度达标才恢复。防抖参数登记待确认 #AI-05。

### B-07 AI 训练：纠错队列「续保留」与「5 秒过期」冲突（高）

- 现状：表格「左下角队列：入队后独立保留 5 秒，再淡出」；同一表格「同错误持续：已入队时**续保留时间**，不重新放大」
- 冲突：只要错误持续就续期，队列项可能永不淡出，与「保留 5 秒」「最多两条、第三条挤出最早一条」自相矛盾；同时也没有说续期上限
- 建议写法：
  > 入队项默认保留 5s；若同一错误仍在持续，可续期一次，单条最长存活 15s，到期必淡出；续期不改变队列顺序、不触发重新放大；队列满 2 条时新错误挤出最早一条（被挤出项记录一条『未展示』日志供内容侧评估）。

### B-08 AI 训练：「本规范下限」指代不明（中）

- 现状：「最大字号不小于**本规范下限**」，而排版表里只有「弹出态 48～36px / 入队态 40～28px」，两张表都没标哪个是下限
- 建议：改为「弹出态字号 48px 起排、下限 36px；入队态 40px 起排、下限 28px。**下限**即两段区间的较小值，不得低于该值」，并在表格里用「起排 / 下限」两列拆开

### B-09 AI 训练：评分阈值缺失（高）

- 现状：只有四级名称与颜色，「0～100 分及等级阈值沿用算法约定」；阈值实际是验收必需的判据
- 建议：给出占位阈值并标注待确认（例：完美 ≥90 / 较好 75–89 / 良好 60–74 / 未达标 <60，待算法确认），这样 UI 联调、测试用例、等级色验证都能先跑起来

### B-10 AI 训练：灯带与床体行程冲突（中）

- 现状：「AI 期间停用原行程灯效对同一灯带的控制」；但 AI 训练中用户可从全局面板折叠/移动床体（规则允许），此时灯带应指示行程还是评分？
- 建议写法：
  > 优先级：安全告警/急停 > 床体行程指示 > AI 评分闪烁。AI 训练期间若发生床体移动，灯带临时切换为行程指示并在移动结束后 1s 恢复评分闪烁；恢复不补播期间的评分事件。

### B-11 全局快捷设置：训练中能否唤出 + 手势冲突（高）

- 现状：只写「底部上滑或左侧评审入口打开」，未区分是否在训练中、是否全屏、是否暂停态
- 影响：训练中误触上滑会打断训练（与「暂停和停止入口必须可达」的误触防护要求冲突）
- 建议写法：
  > 训练中（非暂停态）底部上滑需先点击一次才能唤出（防误触），唤出自动暂停训练；全屏主画面下上滑仅在底部 8% 区域生效，其余区域上滑不响应；面板展开时下滑/点遮罩收起，收到收起事件不改变训练状态。
- 同时补齐：面板高度 72% 换算值（1080×1920 → 约 1382px）；亮度/音量滑杆步长（建议 1%，长按连续但 100ms 节流）

### B-12 设置：语言切换的生效范围自相矛盾（高）

- 现状：「选择主题／语言**即时应用当前设备新增页面与弹层**」；同一模块又写「每个详情**继承当前端主题与语言**」
- 矛盾：若只作用于新增页面，旧页面会与新页面中英混排；若作用于全设备，则「新增页面」的限定没意义
- 建议写法：
  > 语言切换为设备级即时生效：已本地化的页面与弹层立即切换；未本地化的旧页面保持原语言并在设置页说明「部分旧页面暂不支持该语言」，不得出现同屏中英混排标题与按钮。语言切换不清空训练进度与设备状态。

### B-13 训练数据与次数：三种数据形态未定义（高）

- 现状：「无可用数据与 0 次区分，断连或未知不得伪造新数值」——但**没写无可用数据长什么样**
- 另外：「最低单边 3kg、双边 6kg 不调整」语义不明（是阻力下限不随本版改动，还是次数统计下限？）
- 建议：
  1. 明确三态展示：`0 次`（有数据且为零）/ `—`（设备断连或状态未知）/ `--`（尚未开始训练，无会话）。只允许这三种，不允许空白
  2. 「最低单边 3kg、双边 6kg 不调整」改写为「阻力下限沿用现有单边 3kg / 双边 6kg，本版不改动」
  3. 容量/输出能量/卡路里补口径占位：`容量 = Σ(单次阻力 × 次数)`，其余沿用现有计算来源，标注「口径待确认 #DATA-02」

### B-14 常见问题：反馈通道消失 + 运营规则缺失（高）

- 现状：PRD/网页均写「原帮助与反馈更名常见问题，不增加反馈表单、工单或记录」
- 问题：改名后用户端**完全没有反馈入口**——遇到 FAQ 未覆盖的问题无处可去。对硬件产品这是明确的运营风险（客诉无处落、问题无回流）
- 建议：① 明确「FAQ 详情页底部保留『联系客服』（电话/在线客服），不属于本次新增范围」或「本期确实不做，客服入口沿用原设置页」；② 补 FAQ 运营规则：无搜索但有分类；单分类条数上限；排序按后台 sort 值 + 置顶；富文本白名单（允许 p/h3/h4/ul/ol/li/strong/img/a，禁止 script/style/iframe/on* 事件，外链需二次确认）

### B-15 APP 账号注销：合规与安全规则缺口（高，最高优先）

| 缺口 | 现状 | 建议 |
| --- | --- | --- |
| 数据处置清单 | 只写「以确认政策为准」 | 必须列出：删除（账号资料、训练记录、体测数据、偏好）、保留（依法需留存的交易/发票，期限 N 年）、匿名化（统计数据）三类，逐项给期限。这是合规硬要求，不能留给「政策」 |
| 验证码风控 | 只有 6 位/5 分钟/30 秒重发 | 补：连续输错 5 次锁定 15 分钟；同账号 24h 内最多发送 10 次；异地/异常设备触发二次校验 |
| 冷静期 | 未提 | 明确「即时生效」还是「T+N 天冷静期可撤销」。两种体验差异极大，直接影响页面文案（「已注销」vs「注销申请已提交，N 天内可撤销」） |
| 绑定关系 | 未提 | 明确注销前需处理的绑定：设备绑定、家庭/子账号、第三方登录、订阅（原扣费平台）。给顺序与阻断提示，避免注销后设备仍挂在已注销账号下 |
| 再注册 | 未提 | 明确注销后同一手机号/邮箱能否立即重新注册，以及历史数据是否可见 |
| 结果未知 | 只写「先查询状态」 | 补查询节奏（如每 5s 一次、最多 6 次）与超时后的兜底文案（「提交已受理，请稍后在账号与安全查看结果」） |

### B-16 APP 设置：偏好跨端同步冲突（中）

- 现状：「账号偏好正式跨端同步语义一致」；设备端也能改同一偏好（设置→训练偏好）
- 缺口：两端同时修改、离线修改后上线如何合并，未定义
- 建议：以服务端最后写入为准（LWW），另一端进入页面时拉取；离线修改暂存本地并在联网后以服务端值覆盖 + 提示一次「偏好已在其他设备更新」

### B-17 我的：规则过薄（中）

- 现状：仅 9 句，其中 4 句是「保留原…」
- 缺口：用户数据字段与统计周期、近期记录条数与口径、退出登录的二次确认文案、切账号缓存清理范围（是否含本地外观偏好）、账号失效态的页面态
- 建议：至少补齐「页面元素 → 数据来源 → 口径 → 空/异常态」四列小表

### B-18 系统性：「沿用原…」13 处无基线（高）

- 实测统计：规则正文共 9458 字，「沿用」13 次、「待确认」11 次、「原」24 次

- 问题：新加入的研发/测试无法验证，评审也无法判断「原规则」是否被本次改动破坏
- 建议：附录新增「沿用基线索引」表——`沿用项 | 基线文档与章节 | 基线版本 | 是否受本版影响`，正文的「沿用原 X」改为「沿用基线 B-04」

### B-19 无需求编号（高）

- 现状：全部规则为自然段，无 FR 编号
- 影响：无法与测试用例、RTM、缺陷单互链；评审意见只能按段落引用（本报告已不得不按「位置+引文」描述）
- 建议：每条规则加锚点编号，如 `FR-BED-03`、`FR-AI-07`；网页侧用 `<h3 id="fr-bed-03">`，支持 `index.html#fr-bed-03` 直达；测试用例直接写用例覆盖的 FR 列表

### B-20 UI 文案未集中管理（中）

- 现状：弹窗文案、错误提示、兜底句散落正文（如「当前账号已失效，请先结束训练。」「请让全身出现在镜头里…」「Review the demonstration and adjust your form.」）

## 四、C 类：网页自身与评审工具问题

### C-01 AI 训练模块 HTML 结构非法（高）

实测该模块结构为：`<p><h4>主画面与小画框</h4></p>`、`<p><p>正文</p></p>`、表格内 `<tr>` 被 `<p>` 包裹且 `<p>` 直接出现在 `<tbody>` 里。

- 浏览器容错后仍能显示（实测两张表被修复为 10 行 / 5 行，表格数据未丢），但：
  1. 编辑态（contenteditable）光标行为会错乱，回车容易产生新的非法嵌套；
  2. 「导出全部修改」会把脏结构写回 `rulebook-data.js`，问题被固化并扩散到 `rules.html`；
  3. 后续做样式（如表格斑马纹、小节折叠）会因结构不可预期而失效。
- 优化方案：把 AI 训练与 APP 账号注销两个模块重排为规范结构（`h3 → h4 → p / table`，表格内只允许 `thead/tbody/tr/th/td`），清理空 `<p></p>`；建议加一条构建前校验（`<p>` 内不得含块级元素、`tbody` 内不得含 `p`）纳入现有 `verify-*.cjs` 体系。

### C-02 残留文档编号（中）

- 「2.5 灯带相关逻辑」直接显示在网页标题里，与同页其他无编号标题并列，读起来像文档草稿残留
- 优化：改成「灯带与评分联动」，编号放到锚点 ID 里

### C-03 规则编辑器无「恢复原始 / 修改历史」（中）

- 现状：编辑即覆盖写入 localStorage；只有 `训练准备` 配了 `MotionRuleRevisions`，其余 11 个模块改动不会归档；导出会直接生成同名 `rulebook-data.js`（无 diff 预览）
- 风险：评审现场误改无法一键还原；多人评审互相覆盖
- 建议：① 增加「恢复原始规则」按钮（丢弃该模块 localStorage 覆盖）；② 每个模块都登记 revision；③ 导出前弹出「已改动模块列表 + 逐段 diff」，确认后才下载

### C-04 长文档无导航（建议）

- 单模块规则最高 3562px，无目录锚点，不能在模块内跳转到「待确认 / 异常」；也没有「只看待确认项」筛选
- 建议：模块头部生成小节锚点条（本次修改/页面与状态/操作规则/异常/联动/验收/数据来源/状态保存/适用边界），并加一个「仅显示待确认标注」开关

### C-05 术语不统一（建议）

| 现状混用 | 建议统一 |
| --- | --- |
| 中停 / 中途停止 | 中途停止 |
| 准备完成 / 确认（简洁模式） | 均写「准备完成」，简洁态按钮文案单列 |
| 收起 / 关闭（面板） | 收起 |
| 交换 / 切换（小画框、画面） | 主次画面交换 / 模式切换 |
| 沿用原 / 保持原 / 与原一致 | 统一「沿用基线 B-xx」 |

### C-06 Demo 默认外观与规则不一致（建议）

- 规则写「设备初始深色中文」，但页面「外观」默认 `浅色 · 当前默认`，`#frame` 初始 class 也是 `frame device light`
- 影响：评审看到的第一屏与规则声明的出厂默认不符
- 建议：要么把默认改为 dark 并在左栏注明「出厂默认：深色/中文」，要么把规则改为「Demo 默认浅色，出厂默认深色」

### C-07 资源 404（建议）

- 实测控制台：`GET /device-baseline/css/assets/card3.jpg → 404`
- 建议：补图或删除引用，避免评审时看到空白卡片

### C-08 双入口同源但同缺（提示）

- `rules.html` 与右栏读取同一份 `rulebook-data.js`，所以 4 个全局章节在总览页同样缺失，补一处即补两处；补完后建议在总览页顶部加「范围 / 主流程 / 待确认 / 验收口径」四个快捷链接

### C-09 「演示状态 · 仅供评审」与规则标题同级（建议）

- 评审按钮组使用的 H3 与「页面与状态」「操作规则」同级，视觉上抢规则标题的层级
- 建议：该类评审控件的标题改为小号说明文字（或 `h4` + 弱化色），与规则正文区分开
